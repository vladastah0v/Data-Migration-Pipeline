# Верификация миграции

Команда `verify` проверяет сохранённый запуск с завершённой загрузкой. Используйте UUID из вывода `migrate` или `status`. Для текущей схемы target нужна ревизия `target_0004`, которую применяет `migration-pipeline init`.

```bash
uv run --locked migration-pipeline verify --run-id "$RUN_ID"
uv run --locked migration-pipeline verify --run-id "$RUN_ID" --json > verification.json
uv run --locked migration-pipeline status --run-id "$RUN_ID"
```

Из Docker команда запускается через сервис `migration-runner`.

```bash
docker compose --profile tools run --rm migration-runner verify --run-id "$RUN_ID"
```

## Что проверяется

| Проверка | Условие |
| --- | --- |
| Количество записей | Число исходных записей равно сумме подтверждённых target ID и отклонений запуска. Сверяются счётчики запуска, подтверждённые партии, границы контрольных точек и признаки карантина. |
| Полнота | Каждый исходный ID присутствует в целевой таблице или подтверждён журналом отклонений. Лишние legacy ID в target и ссылки принятых строк на отклонённых родителей считаются расхождениями. |
| Внешние связи | Проверяются ссылки целевых заказов, платежей, событий, позиций, контактов, адресов и атрибутов. Соответствие связи конкретному родителю проверяется по его legacy ID в составе контрольной суммы. |
| Денежные значения | Сверяются суммы заказов и платежей, цена, количество и `line_total` каждой позиции. Проверяются формула `line_total = quantity × unit_price`, сумма позиций каждого заказа и агрегаты по валютам. Валюта платежа берётся из связанного заказа. Денежные значения обрабатываются как `Decimal`. |
| Контрольные суммы | Для каждой из восьми таблиц сверяются SHA-256 и количество нормализованных строк. Состав включает контакты, адреса, атрибуты и позиции заказов. |

Сверка рассчитана на target, выделенный для проверяемого набора legacy. Если в target уже была строка с ID, отклонённым в текущем запуске, отчёт учитывает её в `rejected_present_in_target`. Такой ID засчитывается как отклонённый, а данные этой строки и её собственных дочерних строк исключаются из контрольных сумм и денежных итогов. Проверка внешних связей охватывает все целевые бизнес-таблицы.

## Контрольные суммы и повторная загрузка

Источник проходит те же преобразования, что при загрузке. Target приводится к тому же набору полей, а UUID родителей заменяются на legacy ID. Формат версии 1 использует UTF-8, фиксированный порядок полей, сортировку по legacy ID и содержимому дочерних строк, даты и время в едином формате, точные числа и ключи JSON в порядке сортировки. Порядок элементов массивов JSON сохраняется. SHA-256 накапливается по партиям. Размер партии загрузки, значения служебных UUID и порядок ключей JSON не влияют на результат.

При повторной загрузке того же снимка с неизменными данными `status` показывает количество неизменённых записей. `verify --json` позволяет сравнить наборы `checksums` двух запусков. Сверка читает зафиксированный снимок legacy по UUID запуска и использует одну транзакцию `REPEATABLE READ` на target. На время проверки действует та же блокировка PostgreSQL, что при миграции. Результат относится к состоянию target, видимому в транзакции проверки.

## Статус и коды выхода

| Результат | Статус запуска | Код |
| --- | --- | --- |
| Все проверки пройдены | `SUCCESS` | `0` |
| Все проверки пройдены с подтверждёнными отклонениями | `SUCCESS_WITH_REJECTIONS` | `0` |
| Нарушена обязательная проверка | `FAILED_VERIFICATION` | `1` |
| Загрузка завершилась с ошибкой | `FAILED_MIGRATION` | `1` при вызове `verify` |

Если UUID отсутствует, загрузка ещё не завершена, снимок сменился или база недоступна, команда возвращает код `1` и оставляет прежний статус и отчёт. Код `2` обозначает ошибку параметров или конфигурации. Повторный `verify` проверяет актуальное состояние target и сохраняет новый результат под тем же UUID. При `FAILED_MIGRATION` сначала возобновите загрузку через `resume`.

При `--json` в stdout поступает итоговый JSON с количеством строк, аудитом отклонений, числом нарушенных ссылок, денежными расхождениями, статусами проверок и хешами. События `verification_batch_checked` и `verification_completed` пишутся в stderr. Событие партии включает число проверенных строк и скорость. Последний отчёт хранится в `migration_runs.verification_report`, время сверки в `migration_runs.verified_at`.
