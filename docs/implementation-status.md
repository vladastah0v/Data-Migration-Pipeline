# Состояние реализации

## Этап 1. Основа проекта

- Создан Python-пакет с CLI на Typer и Rich. Зависимости зафиксированы в `uv.lock`.
- Конфигурация подключений загружается из окружения и `.env`. Команда `migration-pipeline check` проверяет настройки, подключается асинхронно к обеим базам и сверяет версию PostgreSQL.
- Compose запускает два независимых экземпляра PostgreSQL с отдельными именованными томами, локальными портами и проверками готовности. Прикладные роли создаются при первичной инициализации томов.
- Скрипт инициализации включён в образ PostgreSQL. Это устранило ошибку запуска скрипта с внешнего диска в Docker Desktop.

## Этап 2. Схемы PostgreSQL

- Созданы модели legacy CRM, нормализованные модели target и служебные таблицы запусков, партий, checkpoint и ошибок.
- Добавлены ключи по исходным идентификаторам, внешние ключи, проверки денежных сумм, уникальность платёжных ссылок и ограничения на записи служебных таблиц.
- Подключены независимые истории Alembic. Команда `init` применяет `legacy_0001` и `target_0001`. В Docker используется отдельный сервис `schema-init` с учётными данными владельцев.
- Реализована фиксация неизменяемого снимка legacy. PostgreSQL блокирует запись после фиксации, а UUID снимка хранится в метаданных запуска на стороне target.

## Этап 3. Генератор синтетических данных

- Добавлены CLI-команда `seed`, скрипт запуска и сервис Docker `seed-runner`. Генератор использует только подключение к legacy.
- Поддерживаются профили Small, Medium и Large, фиксированный seed, размер пакета COPY, настройка доли дефектов и повторов email.
- Генерация сохраняет связи, порядок событий и согласованные суммы для чистых данных. PostgreSQL проверяет итоговые объёмы перед фиксацией снимка. При ошибке вся запись откатывается.

## Этап 4. Извлечение данных

- Добавлено асинхронное пакетное чтение клиентов, заказов, платежей и истории статусов. Партии упорядочены по первичному ключу `BIGINT`.
- Перед чтением проверяются версия PostgreSQL, схема legacy и UUID зафиксированного снимка. Чтение продолжается строго после переданного ID.
- Команда `extract` выводит прогресс, итоговые счётчики и JSON-события по партиям. Размер партии настраивается в пределах 1–10 000 строк.

## Этап 5. Трансформация данных

- Реализованы преобразования клиентов и контактов, адресов, атрибутов, заказов и позиций, платежей и истории статусов. Проверяются обязательные поля, денежные суммы, даты, JSON и связи.
- Добавлены политики `strict`, `skip` и `quarantine`. Повтор платёжной ссылки при другом legacy ID считается конфликтом. Совпавшие email включаются в отдельный технический отчёт.
- Команда `transform` проверяет зафиксированный снимок. Связи и повторы между партиями проверяются во временных таблицах PostgreSQL.

## Этап 6. Загрузка в target

- Реализованы одиночный и пакетный INSERT, UPSERT и бинарный COPY через временные таблицы с последующим слиянием.
- Загрузчик получает UUID родителей по legacy ID, загружает связанные строки в порядке зависимостей и возвращает счётчики по исходной сущности и целевым таблицам.
- Повтор идентичной записи сохраняет существующие данные и UUID. Для UPSERT и COPY предусмотрена явная политика обновления разрешённых полей.
- Запись использует savepoint в транзакции вызывающей стороны. Таймаут охватывает операции партии и ожидание блокировки.

## Этап 7. Оркестрация миграции

- Добавлены команды `migrate` и `status`. Оркестратор проверяет схему каждой базы и зафиксированный снимок, создаёт запуск с параметрами и конфигурационным хешем.
- Запись в target, отклонения, партия, контрольная точка и счётчики фиксируются одной транзакцией. Структурированное событие публикуется после COMMIT.
- Состояние `LOADED` обозначает завершение загрузки. Статус `FAILED_MIGRATION` и причина сбоя сохраняются отдельной транзакцией при доступном target.
